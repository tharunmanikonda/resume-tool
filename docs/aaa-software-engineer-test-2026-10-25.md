## What this posting is asking for

Software product delivery on one or more of iOS, Android and web; reliable, secure, performant implementation; problem decomposition and troubleshooting; collaboration and independent decisions; AI-assisted coding/debugging/review; and API versioning. Agentic systems are explicitly a strong plus, not the central required role. The posting does not require a candidate to claim production ownership across all three platforms.

The source-backed story should therefore emphasize application implementation, API/security/performance work, testing, collaboration and the actual use of AI development tools. Native Swift projects support platform breadth; genuine AI system work supplies additional relevant evidence without becoming the whole professional identity.

These are concise accomplishment signals. They do not need to contain a complete project architecture or measurement methodology. Review should flag invented mechanisms, misleading attribution and unsupported merges, not penalize concise wording merely for leaving out intermediate steps.

## Remaining targeting problem

Analysis chose `agentic_ai_engineering` and ranked agentic systems among the top three requirements. Its own supporting quotation includes “is a strong plus,” so the input retained preference wording but did not preserve its relative priority.

Synthesis then chose **Applied AI Software Engineer**, opened the summary with applied AI and filled it with classification, anomaly detection and AI infrastructure. It omitted Copilot/Cursor despite their direct relevance and presence in project evidence. Final review corrected the headline to Software Engineer and added the tools, but left the AI-led summary intact. This is a partial targeting correction, not a complete resolution.

The lesson is narrower than “AI is wrong for this JD”: genuine AI work is relevant and valuable here. The required software/product work and AI-assisted development should establish the main story; optional agentic depth should strengthen it without determining the whole role category.

## Evidence limits and editorial review

- Source material supports LLM pipelines and RAG, but not necessarily tool-use loops or multi-step autonomous agents. The final draft does not need to invent those to show useful AI experience.
- API implementation is present; explicit versioning strategy is not established. The preliminary API Versioning skill was removed during synthesis. Do not imply REST alone proves versioning.
- Native Swift projects exist; keep project work distinct from professional mobile employment.
- Some familiar source-derived phrases remain: dashboards credited with reduced UI latency, JWT tied to data-integrity failures, and tests described as detecting and fixing defects. These are wording/attribution issues, not proof the achievements are false. Tighten them only with a source-supported description; do not demand the whole project story inside the bullet.
- McKinsey prompting bullets introduce routing/relevance explanations more specific than their original source accomplishments. Those explanations should not be assumed solely to fill a causal sentence slot.
- Internal audit findings are fallible. Its generic numerical-shortfall note conflicts with the measured final coverage counts. It also underrecognizes candidate project/qualification context in some gaps. Do not treat its score or every gap as an authoritative factual assessment.
